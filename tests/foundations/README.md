# Continuation contract checks

Run with Node.js builtins only:

```text
node scripts/validation/check-foundations.mjs
node scripts/validation/check-foundations.mjs --json
node --test tests/foundations/*.test.mjs
```

`--root DIRECTORY` checks another checkout. Exit 0 means contract integrity,
1 means failed validation and 2 means invalid command-line options. It imports
the existing planning validator and does not modify existing requirements,
tasks, gates, state or assignments. All new records initially say `open` and
`not_run`, with `not_implemented` where implementation stages apply. Test commands
for language acceptance are initially null because proposed groups are not
implemented test runners.

The inherited 147 requirements (139 mandatory and eight future), 38 tasks and
19 gates remain separate from the 15 L-feature contracts, seven C-continuity
contracts and 12 intermediate FC1 checks. Sixteen groups map positive, negative
and injected-defect boundaries. Thirteen named expansions preserve broad goals
without reclassifying required foundations. Reflection IDs and both directions
of FC1 mappings are checked. FC1 is an experimental preview and cannot waive
inherited HATCH requirements. A mapped FC1 subset is not equivalent to the whole
HATCH feature.

`planning/contract-migration.json` captures the old IDs, scope, evidence references
and original source/contract identity. Current inherited statuses can evolve;
historical evidence cannot disappear from its requirement's evidence list.
Original planning Git-blob hashes identify provenance, not fresh test results.
The separate pinned `.py` grammar identity and all 278 production IDs are retained.
All feature changes have an explicit reason for revision 1.3 revalidation.

New feature evidence has a separate schema from inherited requirement evidence.
Each referenced repository-relative JSON object has these fields:

- `subject_id`: an L, C, FC1, TG or X ID, with `test_group` from its mapped groups.
- `kind`: `positive`, `negative` or `defect_injection`; `contract_revision`: `1.3`.
- `source_commit`: a full 40/64-character lowercase hash or null;
  `dirty_tree_sha256`: a 64-character lowercase hash or null. At least one tested
  source identity must be supplied.
- `host`, `target`, actual `command` arguments, `tool_versions`, `exit_code`,
  `result`, `timestamp`, `log_path`, `log_sha256` and `limitations`.

A passed record needs command exit 0 and an existing nonempty in-repository log
whose exact bytes match SHA-256. A subject's verified state needs passed positive,
negative and injected-defect evidence for every mapped group, all at one exact
source/target identity. A verified test group also needs an implemented command.
Old evidence missing a revision field remains its original inherited evidence;
it cannot verify a new feature by association.

For `defect_injection`, add `defect_injection` with a meaningful `defect_id`,
`mutant_source_sha256`, `control_result: "passed"`, `mutant_result: "failed"`,
a nonzero integer `mutant_exit_code` and `detected: true`. Exit 0 on the outer
record belongs to the verification harness; the intentionally broken feature
must make its acceptance test fail. A mutation test remaining green is rejected.

These are necessary record-consistency conditions. The validator does not execute
the recorded commands, establish their honesty, verify that Git objects exist,
prove a mutation occurred, or establish complete behavioral coverage. Runtime,
native artifact and review evidence must establish those facts separately.
Synthetic records/logs generated by unit tests stay in disposable temporary
directories and are explicitly labeled; they are not NAJA acceptance evidence.
